# Contract catalog and authority boundary

This directory contains versioned wire contracts for the private benchmark
ledger and the public release boundary. A matching JSON Schema proves only the
shape of a document. Where a Python semantic validator exists, both validations
are required: the executable validator enforces canonical digests,
cross-field state rules, stable identities, and authority constraints that are
not safely expressible as schema comments.

Checked-in examples are synthetic, draft, report-only, or unavailable. They are
test fixtures, not governance decisions, source certifications, scheduled
work, incident acknowledgements, notification deliveries, claims, publication
approvals, or frontend inputs.

## Contract families

| Family | Contracts | Authority ceiling |
| --- | --- | --- |
| Public containment/release | `official-release-artifact-v1`, dormant `official-release-artifact-v2`, `official-release-authorization-v1`, `official-feed-candidate-v1`, `legacy-inventory-v1` | The tracked v1 artifact can state only that Official is unavailable. The v2 parser can select only canonical bytes with an exact, separately governed authorization pin; no such artifact or authorization is tracked. Candidate and legacy reports are never frontend inputs. |
| Bounded coverage/discovery | `coverage-universe-v1`, `coverage-census-v1`, `discovery-target-v1`, `discovery-candidate-v1` | Defines and reports bounded product scope or permits candidate reconnaissance after a separate decision. It cannot certify a source, capture a result, publish, or enable Official mode. |
| Source capture policy/evidence | `source-contract-v2`, `source-check-receipt-v1` | Describes the exact conditions a separately certified source revision must satisfy and records one attempted check. The contract cannot certify itself; the receipt cannot retroactively authorize a fetch or claim. |
| Benchmark and evaluated identity | `benchmark-definition-revision-v1`, `evaluation-subject-v1`, `identity-decision-v1` | Preserves immutable benchmark editions and typed systems. A draft definition is not active, and an observed/raw system label is unresolved until an authorized append-only identity decision says otherwise. No decision rewrites a captured claim or promotes validation/publication. |
| Scheduling and operations | `scheduled-cycle-v1`, `scheduled-job-attempt-v1`, `ops-incident-v1`, `review-work-item-v1`, `notification-intent-v1`, `notification-receipt-v1` | Records deterministic slot/job/attempt and append-only operational history. Scheduling cannot bypass source admission. Incident, work-item, or delivery state cannot change evidence, certification, review, publication, or release state. External routes remain disabled until recipient/privacy authority exists. |
| Recovery evidence | `recovery-checkpoint-v1`, `recovery-restore-receipt-v1` | Binds one exact terminal-cycle database backup to complete relational/object denominators and records one verified new-target recovery map. It cannot prove provider independence, retention, production RPO/RTO, role/ACL recovery, cutover, certification, capture, publication, or frontend eligibility. |

## Validation layers

1. Parse every schema and validate it against JSON Schema Draft 2020-12.
2. Validate each example against its matching schema with format checks.
3. Run the matching pure Python semantic validator and verify the canonical
   self-digest or fingerprint.
4. Run available pure cross-document validators over the exact supplied
   immutable records. For example, every scheduled recheck attempt must resolve
   exactly one deterministic source-check receipt and agree on slot, source
   revision, job, attempt, fencing token, terminal semantics, execution interval,
   receipt ID/digest, snapshot ID/content digest, and incident-reference
   denominator. The DATA-09 persistence boundary resolves supported IDs and
   effective decisions to exact immutable relational records; unsupported
   terminal referent types fail closed. This durable lookup does not activate a
   scheduler, certify a source, or authorize a side effect.
   Recovery validation additionally recomputes the exact 36-table inventory,
   cycle/object sets, seven lineage families, producer/inspection bindings,
   receipt duration, self-digests, and authority ceilings. Runtime recovery
   must separately re-resolve the manifest's immutable publication and every
   recorded object copy before a receipt exists.
5. Enforce live DNS/connected-peer, TLS, storage, role, fencing, and delivery
   controls at the future private runner/provider boundary. An offline contract
   validator cannot prove those runtime facts.

Contract validators must remain deterministic and side-effect free. They do
not read the clock, environment, filesystem, network, database, provider, or
frontend state. Receipt timestamps are immutable recorded facts supplied by a
caller; they are never silently generated by a validator.

## Containment

Do not import any coverage, discovery, source, identity, schedule, incident,
work-item, or notification document into the SPA. During FEED-01 containment,
`src/data/official/export.unavailable.json` is the only frontend artifact.
Likewise, do not use a valid fixture to create a source revision decision,
schedule a live check, initialize or migrate a database, send an alert,
provision a provider, or publish an Official result.

Recovery documents are also never SPA inputs. Their local/disposable operator
workflow is documented in the
[provider-neutral recovery runbook](../runbooks/provider-neutral-recovery-checkpoint-and-restore.md)
and [ADR-010](../adr/ADR-010-provider-neutral-recovery-evidence.md).

The durable local/disposable representation and live-disabled composition root
are governed by
[ADR-009](../adr/ADR-009-operational-persistence-and-inert-runtime-composition.md).
Their presence does not change any contract's authority ceiling.
